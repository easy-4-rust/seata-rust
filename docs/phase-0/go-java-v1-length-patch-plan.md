# GO-V1-FAIL-001/002 修复候选验证

依据：[失败响应差异](known-go-v1-failure-divergences.md)、[WP-00](v1-implementation-acceptance-checklist.md)、ADR-0003/0007/0008。Java权威提交与固定Go参考提交不变；此文是现有WP-00的实施步骤，不另建规格事实源，不修改验收标准。

目标是在可审查的独立Go源码副本中修复BranchReportResponse(type14)与GlobalLockQueryResponse(type22)失败文本长度。只提供明确标识的兼容补丁候选，不覆盖原始参考实现、不改原样例，也不声称上游已修复或全部Go兼容。

1. 增加真实Java编码/解码测试：两类失败响应的空/短文本、127/128、255/256、32767字节边界、ASCII32768截断、有效UTF-8文本及成功响应/lockable控制。捕获实际序列化字节并断言独立字段。
2. 从已校验归档新建D盘独立Go副本。加入只调用原生codec的回归测试，先证明原版在Java字节输入/输出上失败；不能以新增补丁函数的缺失编译错误代替RED。
3. 最小修改两类codec：读写16位文本长度，使用已有16位文本上限；生成可重复应用的unified diff及原/补丁文件哈希。
4. 同一测试在补丁副本通过，执行受影响的完整codec/bytes包测试、原29样例/六帧回归及Rust独立探针回归；原版参考源码在前后保持字节一致。
5. 保留原版RED、补丁GREEN、Java报告/执行源、补丁/源码闭包和所有限制，完成只读审查。调查结论与上游问题状态分别记录。

本轮长度修复的互操作范围是Java可解码的非负signed-short UTF-8字节长度（最多32767），以及可验证的ASCII截断行为。Java按UTF-16字符截断而后写入short长度，超大多字节文本另有边界风险；不能从本轮正常UTF-8样例推断所有超大Unicode输入兼容。畸形流的严格解码、Go错误码19/20及扩展枚举分叉、缺失59/60 codec、生产Rust协议实现均不因本补丁关闭。

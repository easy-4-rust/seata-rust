# 排他锁键进入TC前的覆盖核查

当前[锁键组件](evidence/lock-key-gate/README.md)只证明固定原方法的格式/次序和原生JDBC值转换。TC登记、实际锁存储、Undo原子性和提交未知恢复继续OPEN；共享锁暂缓事项与本项分开。

2026-11-16更新：[正式来源方法与真实网络/存储观察](evidence/tc-lock-live/README.md)已补齐下述步骤1–3的选定场景证据。15个来源案例、8个实际MySQL生成键/原TC网络场景及25个TC数据库确认点，确认空白、多行空值/分号漏锁和不同二进制值额外冲突。16个原XID均结束、实际锁存储清空，自有进程/容器已清理；这是缺陷事实的正式封存，TC安全门槛仍OPEN。早期未资格化诊断保留，仅用于历史说明，不再作为唯一依据。

[隔离来源方法诊断](evidence/tc-lock-coverage-diagnostic/run_20261116_0118_source/classification.json)实际重新编译固定pin的`AbstractLockManager`，用录制后端调用`collectRowLocks/acquireLock`：普通`t:1`生成一行且调用后端一次；`t:`和`t: `生成零行，acquire返回true且未调用后端；`t:x;broken;later:2`只保留`t:x`而不收集later；原二进制列表`[0, -1]`被逗号拆为两个PK片段。后二者不能直接推断真实锁存储中的互斥丢失或安全性。

这是诊断级原方法调用，尚未完整封存运行前后classpath闭包，未发真实TC请求，录制后端也不代表实际锁存储。原源与Git pin内容匹配，源码、生成class、日志和输出已单独保留；不将这个包列为正式TC Gate通过，也不据此修改锁键字节或接受外部风险。

下一步顺序：

1. 正式冻结来源方法、JDK/编译class、完整运行输入及每个class来源，补齐源方法诊断的证据范围。
2. 在自有原Java TC中，用普通相同行锁冲突作为正控制，再比较空/全空白主键以及分号/二进制键的原分支登记、实际锁行和冲突结果。保持原XID/BranchId，只发送一次；结束原全局事务并清理自有实例。
3. 把观察与实际MySQL原主键、生成器输出连接起来；只有明确证明锁覆盖和失败分类，才决定已声明支持矩阵、原TC候选修复或后续协议策略。不能通过转义/hash改变Java原键而隐藏差异，不能把未闭合问题写成用户已接受。
4. 并行继续完整源案例展开及同连接Undo持久化/分支登记/持久围栏实施。公共COMMIT必须等原门禁与实际故障测试通过；失败不能重放业务SQL，TC拥有事务重试。

本轮验证固定 SQLx/rustls、MySQL 8.4.13 及选定 RSA 证书的有效期与在线轮换，生产源码没有新增行为或接口。

四项现场测试覆盖以下行为。

- 真实 REQUIRE X509 账号拒绝同 CA、同 CSR/密钥的过期与尚未生效客户端证书，当前有效客户端证书对照通过。
- MySQL 自身拒绝重载过期及尚未生效服务端证书，返回 3888，保持旧 TLS 上下文。随后新数据源、元数据及辅助会话仍可通过旧合法证书连接。
- 真实 MySQL 在线重载同 CA 的新叶证书与密钥后，新池租约和旧事务发起的新辅助握手继续成功。换成另一个 CA 后，旧信任配置的新池连接及辅助会话拒绝，原事务污染并回滚，独立业务值为 10。同一个双 CA 配置分别连接 CA2 和恢复后的 CA1，更新为仅 CA2 的新配置也通过。
- SQLx/rustls 对过期及尚未生效服务端证书的直接握手拒绝通过受控 TLS 前端验证。该前端先接收真实 MySQL greeting/SSLRequest，再终止前端与后端两段 TLS，按 FIFO 转发真实认证及查询字节。后端始终验证合法 CA1；前端可呈现失效证书。前后合法证书基线完成真实业务，坏证书拒绝新连接及旧业务事务的新辅助握手。旧桥业务连接仍能成功 ROLLBACK，独立 MySQL 观察者仍读原值。

不能将桥用例描述为 MySQL 直接呈现失效证书或端到端 TLS 直通。独立 observer 是直连 MySQL 会话，旧桥会话存活由 held.rollback 成功证明。有效削弱控制将 VerifyIdentity 改成 Required，使过期服务端断言失败，随后精确恢复源码并重跑正常用例。

端口链为 Windows 43319 TLS 前端 → Windows 43318 字节中继 → D 盘 WSL Ubuntu 自有 MySQL 43317。中继沿用已归档的 fastjson-undo-native/run_20261120_owned_wsl_mysql/wsl_stdio_relay.py。桥每条连接的两个 SSL 对象由同一线程非阻塞处理，避免并发操作同一 SSL 对象。初版夹具的并发 SSL 转发导致合法基线失败，诊断日志保留，该失败不算生产行为 RED。

测试入口持同一进程内 Tokio 锁，保护共享证书文件、业务表和服务器 TLS 上下文，最新现场以 --test-threads=4 验证。锁不保护其他测试进程，所以本轮夹具仍由唯一拥有的运行器使用。

所有证书现场签发，有效证书两天，失效样例分别为 2010 与 2035，未修改系统时钟。独立 OpenSSL 核验过期/未生效错误，只有公共证书归档，测试私钥留在 D 盘。重现时需重新生成证书并设置新的 D 盘证书目录。

原客户端 PEM 配置是数据源建立时的内存配置，本轮通过新数据源提供新 CA 或过渡信任列表，不实现证书文件热监听。轮换不追溯撤销既有 TLS 会话。CRL/OCSP、生产证书发布流程和其他算法/链继续按原计划验收。

首次全量链接遇到磁盘空间不足。两次清理都只删除已核对任务构建缓存绝对目录中的过期 PDB，保留清单和失败日志，源码、数据库数据及验收归档未删除。最终版本工作区日志为成功重跑结果。
